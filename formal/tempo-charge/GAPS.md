# Spec gaps

Each row is a rule draft-tempo-charge-00 leaves out. With its guard off, `TempoCharge/Counterexamples.lean` holds a `decide`-checked trace that breaks the named property; with the guard on, the same trace is rejected at the guarded step (`rejectedAt`), or for row 2 runs without a receipt. Rows 5 and 7 hold with every guard on; row 6 is wording.

| # | Where | Gap | Guard (`Cfg`) | Breaks | Counterexample |
|---|---|---|---|---|---|
| 1 | §Hash Verification; core §Replay Protection, §Concurrent Request Handling | A spent transaction's hash is not refused again: one payment settles a pull challenge and a hash challenge with the same request, after the pull settles or in the window between its broadcast and its settlement | `txSingleUse` | P3 | `G1_violates_P3`, `G1_guard_rejects`, `G1_race_window`, `G1_race_violates_P3`, `G1_race_guard_rejects` |
| 2 | §Settlement Procedure, §Transaction Verification | Pull settlement never requires the broadcast transaction to succeed (only hash settlement does); a reverted transfer gets a receipt | `pullNeedsSuccess` | P1 | `G2_violates_P1`, `G2_guard_no_receipt` |
| 3 | §Proof Verification | No amount check: a free proof settles a non-zero challenge (only clients are told not to) | `proofOnlyZero` | P1 | `G3_violates_P1`, `G3_guard_rejects` |
| 4 | §Ordering, §Transaction Verification step 6, §Hash Verification | Required transfers are not matched one-to-one: two identical splits are satisfied by one transfer, so less than `amount` is paid | `splitsOneToOne` | P1 | `G4_violates_P1`, `G4_guard_rejects` |
| 5 | §Hash Verification, §Hash Payload | A hash credential is bound to neither payer nor challenge: an observer claims another client's public transfer (even one older than its challenge) and the payer's own credential is then refused | none: every guard on | payer gets nothing for its payment | `Gap5_observer_claims_payment`, `Gap5_payer_rejected` |
| 6 | §Shared Fields, §Method Details; intent §Shared Fields | `expires` stays optional (core SHOULD), though the intent calls it REQUIRED for blockchain methods and `validBefore` "no later than `expires`" needs it | modelled: `expires` always present | wording | — |
| 7 | §Transaction Verification, §Transaction Payload | A pull transaction is not bound to its challenge: a holder of the credential submits the transaction signed for one challenge with another same-terms challenge's echo, which settles; the original challenge is then refused | none: every guard on | payer's payment settles a challenge it didn't sign for | `Gap7_pull_rebinds`, `Gap7_payer_rejected` |

- Row 1: with the guard, the server records a pull transaction when it broadcasts it, before settling it, and a hash transaction when it settles it, and refuses a hash credential naming any recorded transaction. Recording a pull transaction only at settlement is too late: core §Concurrent Request Handling serializes only identical credentials, so a hash credential for another challenge can arrive after the transaction is on chain and before it is recorded (`G1_race_*`). Nonce consumption only stops a second broadcast.
- Row 2: with the guard, a reverted pull transaction leaves the challenge open and issues no receipt; the sponsor still paid its fee (§Server-Paid Fees, Denial of Service).
- Row 4: `splits[i]` entries with equal recipient and amount are allowed (only sum < `amount` and each > 0 are required). A split recipient equal to the primary recipient with an equal amount fails the same way.
- Row 5: closing it needs the transfer to commit to the challenge (for example a memo derived from the challenge id) or to the `source` account with `source` authenticated; the draft requires neither. Proof credentials are not affected; pull credentials have the narrower row 7.
- Row 7: a pull transaction reaches only the server, so only a holder of the credential (a proxy, a client library, a compromised client) can rebind it, not an observer of the chain. Closing it needs the same commitment as row 5, such as a memo derived from the challenge id.
